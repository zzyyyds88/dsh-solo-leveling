## 一句话总结

在零改动收录 [keleus/deepseek-pet](https://github.com/keleus/deepseek-pet) 的
基础上，按用户要求移植 [aceice01/dsh-whale-pet](https://github.com/aceice01/dsh-whale-pet)
的 Web 端功能：**WebAudio 音效层（完成琶音/出错安慰/戳音）+ edge-tts 离线语音
（23 条原创台词）+ 长按摸头 + 双击静音 + 三击诊断 + 纸屑庆祝 + 音量系统
（总音量/语音/音效/庆祝分动作，localStorage 持久化）**。全部为纯前端改动，
挂在既有 `shell.overlay` 槽位，不新增 host 插件、不新增路由、不改官方 API。

## 设计要点

- **许可干净**：音效为 WebAudio 振荡器实时合成（零素材）；语音台词文本为原创，
  仅用 edge-tts 作为本地合成工具（whale-pet 是「非商业性使用许可」，本项目
  **未复制**其任何台词文本/音频/角色素材）。
- **纯前端**：全部改动在 client bundle 内，挂 `shell.overlay` 槽位；无 host 半、
  无新路由、无 `/api/*` 依赖，与官方 DSH 零耦合，升级免疫。
- **浏览器自动播放策略**：所有发声路径先 `unlockAudio()`（用户手势解锁
  AudioContext）；语音解码结果缓存，避免重复解码。
- **防话痨**：状态语音 30 秒冷却；出错语音仅在状态真实切换时播放一次。

### 修复（单击叠加摸头）

- **问题**：单击桌宠会触发「戳一戳 + 摸头」两种动作、两套语音。根因：
  `pointerDown` 启动了 700ms 摸头计时器，但 `pointerUp`/`pointerCancel` 未清除它；
  单击时鼠标不动（移动 >5px 的取消分支不触发），700ms 后摸头照常触发。
- **修复**：`handlePointerDownForInteraction` 增加 `cancel`（松手/pointercancel 即清除
  摸头计时器并移除监听）；`pointermove >5px` 与松手共用同一取消路径；
  1500ms 兜底移除监听防泄漏。单击现在只触发戳一戳（音效+语音）。

### 修复（三击叠加戳一戳）

- **问题**：三连击打开诊断面板的同时还会触发一次戳一戳（音效+语音叠加）。
  根因：`handleClick` 的 `clickCount >= 3` 分支在 `clearTimeout(clickTimerRef.current)`
  之前 `return`，前面排队中的 280ms 戳一戳计时器未被清除。
- **修复**：把 `clearTimeout` 移到三击判断之前，三连击只开诊断面板，不再叠加戳一戳。
- **同类审查**：双击（`handleDoubleClick` 清 timer）、长按后松手（`longPressFired`
  守卫）、拖动（`dragged` 守卫 + `cancel` 清摸头 timer）均无同类问题。

### 修复（语音越说越小）

- **问题**：语音台词播放时音量随时间不断变小（句首响、句尾几乎无声）。
  根因：`speakVoice` 的增益包络写成「整句话时长内指数衰减到 0.0001」——
  指数衰减在整句上展开，音量随播放进度持续下降。
- **修复**：包络改为「0.02s 淡入 → 整句**恒定音量** → 末尾 0.08s 淡出防爆音」，
  与短音效（`bell` 的衰减包络本就该渐弱）区分开。

### 修复（完成对话无声音）

- **问题**：完成任务后完成庆祝（琶音+语音）无声。根因：浏览器自动播放策略要求
  AudioContext 必须在**用户手势**中解锁；完成庆祝在 `useEffect`（后台、非手势
  上下文）触发，若用户只发消息、没点过桌宠，AudioContext 一直 suspended，音频静默。
- **修复**：`sound.js` 新增 `armAutoplayUnlock()`——监听页面任意一次
  `pointerdown`/`keydown`/`touchstart` 即创建并 resume AudioContext（幂等，
  触发后移除监听）；`DeepSeekPet` 挂载时调用。用户发消息（点输入框/回车）本身
  就是一次手势，解锁后完成庆祝即可出声。

### 修复（完成/出错语音叠加）

- **问题**：完成任务时语音播两次（`celebrateCompletion` 播一次 + 状态语音 effect
  又播一次）；出错同理。根因：`VOICE_FOR_STATE` 同时包含 `success`/`error`/
  `tool-error`，而 `completionState()` 返回 `kind: 'success'`、出错状态为
  `error`/`tool-error`——事件驱动函数与状态 effect 都命中同一表，各播一次。
- **修复**：拆分为 `VOICE_FOR_EVENT`（success/error/tool-error，由
  `celebrateCompletion`/`comfortError` 一次性播）与 `VOICE_FOR_STATE`
  （approval/waiting/busy/thinking，由状态 effect 播，30s 冷却），两套互不重叠。

### 修复（idle 待机断言，上游测试 14/14 全绿）

- **问题**：上游 `presentation.test.js` 断言 `presentationForState({kind:'idle'}, 99)`
  期待 `'idle'`，但实现是 4 种待机表情均等轮换（`99 % 4 = 3` → `'proud'`），测试失败。
- **根因**：实现违反「待机变体轮换」本意——待机大多数时候应是 idle，偶尔活泼；
  均等轮换让待机表情太花哨，测试断言恰好暴露了这一点（`phase=99` 应回到 idle）。
- **修复**：改实现为**加权轮换** `['idle','idle','idle','cheerful','idle','relaxed','proud'][phase % 7]`
  ——idle 占 4/7，活泼表情各 1/7；`99 % 7 = 1` → `'idle'`，测试原断言直接成立。
- **结果**：上游 14/14 测试全部通过（此前长期是 13/14）。

### 修复（完成对话后仍无声 —— 预热创建 AudioContext + 诊断）

- **问题**：上一轮加了 `armAutoplayUnlock`（手势解锁），但用户测试完成对话后仍无声。
  根因深化：`armAutoplayUnlock` 只在**手势发生时**创建 AudioContext——若用户只是
  打开页面旁观（任务由其他会话触发、没点过页面），AudioContext 从未创建，任务完成
  瞬间在**非手势上下文**首次 `new AudioContext()` → 浏览器强制 `suspended` → 静音。
- **修复**：
  1. `armAutoplayUnlock` 挂载时**立即预热创建** AudioContext（页面加载即有 ctx，
     可能 suspended），手势时再 `resume()`；后续任何发声（含后台完成庆祝）都复用
     这个已存在的 ctx，不再有「非手势上下文首次创建」的路径。
  2. 新增 `audioState()` / `audioError()` 诊断：三击诊断面板显示
     `音频: running/suspended/未创建`、静音、音量、最近音频错误——方便自查
     自动播放策略是否已解锁、解码/播放是否出错。
- **自查方法**：三击桌宠看诊断面板「音频」行：
  - `running ✓` 且有错误行 → 解码/播放问题（把「音频错误」内容反馈）
  - `suspended（点一下解锁）` → 页面从未有点击手势，任意点一下页面再触发任务
  - `未创建` → 桌宠未挂载或脚本未执行

### 修复（完成对话仍无声 —— 普通对话无 running→idle 信号）

- **问题**：用户实测「按钮有声、点桌宠有声、完成任务没声」。音频链路正常，
  根因是**完成庆祝的触发条件不覆盖普通对话**：`celebrateCompletion` 只在
  `snapshot.running` 从 true→false（agent 任务循环）时触发；而普通 LLM 对话
  （流式回答）里 `snapshot.running` 恒为 false，回答期间只有 `partial` 有内容，
  结束后 `partial` 清空回 idle——没有任何代码检测这条路径 → 庆祝永不执行。
- **修复**：
  1. 新增**流式回答完成检测**：`snapshot.partial` 从有到无（且非 running、
     非 error/tool-error）→ 触发完成庆祝。普通对话完成现在有声音/纸屑/台词。
  2. 新增 `fireCompletionCelebration` 去重：running→idle 与流式结束两条路径
     可能先后触发，3 秒内只庆祝一次（防双播）。
- **自查方法**：三击桌宠看诊断面板「音频」行应为 `running ✓`；发一条普通消息
  等回答结束，应听到完成琶音 + 「任务完成啦！」语音 + 纸屑。

### 修复（提问/审批提示无声 + 三连击误触静音 + 音效提醒设置）

- **问题 1（提问/审批提示无声）**：进入 waiting/approval（agent 反问/等批准）时
  应播提示音，但状态语音有 30 秒冷却，连续测试时冷却期内再次进入被挡掉 → 无声。
  **修复**：彻底移除状态语音冷却（用户明确要求）；每次进入 waiting/approval/
  busy/thinking 都播 `playPrompt()` 提示音 + 语音。
- **问题 2（三连击误触双击静音）**：浏览器对快速三连击会在第 2 下派发 `dblclick`，
  原 `onDoubleClick` 直接切静音，导致「三击开诊断 + 静音被切」同时发生。
  **修复**：移除 `onDoubleClick`，双击改由 click 计数判定——第 2 次 click 启动
  450ms 定时器，期间无第 3 下才切静音；第 3 下到达则直接开诊断（不启动定时器），
  三连击不再误触静音。
- **问题 3（音效提醒设置）**：诊断面板新增「音效提醒」设置区，5 个独立开关
  （任务完成提醒 / 出错安慰 / 提问审批提示 / 戳一戳音效 / 摸头音效），
  localStorage 持久化（并入 `deepseek-pet:sound` 的 `alerts` 字段）；
  各发声路径按开关控制，静音播报语音也受「提问审批提示」开关约束。

### 修复（反问提示播成了「请主人同意一下」—— 区分提问与审批）

- **问题**：agent 反问（让你选 1/2/3/4 的 question 交互）时，桌宠播的是
  approval 语音「需要主人同意一下」——提问 ≠ 审批，文案不匹配。
- **根因**：`stateFromSnapshot` 对 approval 与 question 都返回 `kind: 'waiting'`，
  `VOICE_FOR_STATE` 里 waiting/approval 共用 approval 台词，无法区分。
- **修复**：
  1. `pet-state.js`：`state()` 支持 extra 字段；waiting 状态带
     `promptKind: 'approval' | 'question' | 'interact'`。
  2. `deriveVisual` 的 waiting 分支保留 `promptKind`。
  3. `synth-voice.py` 新增 question 台词（"主人，请回答我的问题" /
     "主人，需要你做个选择"），重新合成 25 条。
  4. `VOICE_FOR_STATE` 拆分 approval/question；状态语音 effect 按
     `promptKind` 选择：approval → 「请主人同意」，question → 「请回答我的问题」。
