# DSH 升级适配指南（AI Agent 用）

> 面向**任意 AI Agent** 执行 DSH 官方升级时的强制规则与步骤。本仓库是 deepseek-harness 的 fork 整合包（自维护基线、不跟随官方更新）；官方（`@deepseek-ai/*`）升级时，本仓库的「同包名 fork」与「针对旧版限制的适配层」必须按本指南适配，否则会静默跑旧代码。

## 0. 一条铁律（每次升级先读这条）

**如果官方新版已经实现了与本仓库改动相同的功能 → 优先用官方，删掉/停用本仓库对应的 fork 或适配层。**

- 判断依据是**官方新版源码**，不是 release notes 的字面描述。
- 只有官方**没做、或官方做的方式不满足需求**时，才保留本仓库的 fork / 适配层。
- 保留时也必须把 fork **重 base 到新版官方源码**，不能继续用旧版源码。

## 2. 本仓库对 DSH 的全部改动清单（升级时逐项核对）

> 以下为 rc.2 现状（2026-08 升级核对：官方 0.1.1 未实现与下表任何补丁相同的功能，**无官方化项，全部重 base 保留**）。升级到新版本时逐行对照官方新版源码：已官方化 → 弃用 fork；未官方化 → 重 base 到新版源码。**本表是本仓库 fork/适配层映射的唯一维护处。**

### 2.0 fork 标记与升级自检约定（强制，2026-08-23 起生效）

每个保留的 fork 改动点，其源码处必须有一行含 **`Local fork`** 的注释（写明改了什么、为什么，可引用本指南条目）。这是「语义级定制」在整文件覆盖式重 base 下的唯一可靠锚点。

**升级重 base 完成、进入构建验证之前，必须先跑标记自检并把命中与 §2 清单逐项对照：**

```bash
grep -rn "Local fork" packages apps --include="*.ts" --include="*.tsx" --include="*.yml" | grep -v tests/
```

**清单项在命中里找不到锚点 = 该定制已丢失，先恢复再继续。** 仅靠 git diff 人眼核对「- 方向」不可靠：rc.2 重 base 因此静默丢了三处定制（见 §7），当时构建与单测全绿，谁都没发现。

高危单项自检（重 base 后逐条跑；新加/修改 fork 时同步维护本表）：

| 清单项 | 自检命令 | 期望结果 |
|---|---|---|
| ui-settings scope 恒 host（反向） | `grep -rn "isLoopback ? 'host' : 'memory'" packages/client/ui-settings/src` | **0 命中** |
| ui-settings scope 恒 host（正向） | `grep -rn "Local fork" packages/client/ui-settings/src/client/index.ts packages/client/ui-settings/src/client/settings-scope.ts` | 两文件各 ≥1 命中 |
| session-log-export 不装配 | `grep -n "session-log" packages/bundle/web-app/cordis.patch.yml` | 仅注释行 |
| picker-browse 默认工作目录 | `grep -c "configuredStartPath" packages/host/directory-picker-browse/src/index.ts` | ≥2 |
| profile-boot plain-node 跳过 watch | `grep -n "loader')?.internal !== undefined" apps/cli/src/profile-boot.ts` | ≥1 |
| web-app 默认 HTTPS/0.0.0.0 | `grep -n "?? '0\.0\.0\.0'" packages/bundle/web-app/cordis.patch.yml` | ≥1 |

## 3. 升级流程：基线对比三方合并法（2026-08-23 起，取代整包覆盖）

> 术语对齐：AGENTS.md 红线 3 所称「重 base」，其现行实现方式即本节流程。
> **为什么废弃覆盖**：rc.8→rc.2 采用官方源码整文件平铺覆盖，三处语义级定制被静默抹掉（§7）且构建单测全绿无人察觉。三方合并下，凡上游改动触及 fork 所在代码块必然产生**显式冲突**，无冲突处我方内容必然存活——丢失从静默变成必报错。§2.0 的标记自检由此降级为合并后的第二道保险。

### 3.0 原理与基础设施（一次性，已就绪）

三方合并需要三个输入：**base＝旧版官方 pristine 树、ours＝当前整合包、theirs＝新版官方 pristine 树**。本仓库以本地簿记链维护 base/theirs：

- `refs/heads/baseline/vendor`：基线链，每个提交的树＝某版官方源码的原始状态（未 rescope、零定制），父＝上一基线提交。**本地簿记，不随 push 分发**；换机重建＝重跑阶段一。
- `refs/tags/vendor-upstream/<版本>`：指向官方仓库对应 tag 提交（树对象的取用入口）。
- 链根＝官方 `dsh-v0.1.1-rc.2`（源提交 `b150a551`，pristine 树 `53915efe`）。基线链**每机一条**：
  Linux 机链根 `30edb194`；Windows 机 2026-08-23 重跑阶段一重建，链根 `949eaa2f`
  （commit-tree 元数据不同故哈希不同，树同源等价）。文中引用的链根哈希均须先确认所在机器。
- 已验证（2026-08-23）：当前 HEAD 相对 pristine rc.2 的差异中，核心源码文件的 diff 就是我们的定制本身（如 profile-boot 恰为恢复提交的 24+/17−），噪音主体是文档类——三方合并在本仓库成立。

### 3.1 六阶段流程（AI Agent 逐步执行）

**阶段一 · 情报与新基线导入**（不碰工作区）

```bash
git ls-remote --tags https://github.com/deepseek-ai/deepseek-harness.git   # 选定目标 tag <ver>
git fetch --no-tags --depth 1 https://github.com/deepseek-ai/deepseek-harness.git \
  refs/tags/<ver>:refs/tags/vendor-upstream/<ver短名>
OLD=$(git rev-parse baseline/vendor)          # 当前基线（链尾）
NEW_TREE=$(git rev-parse vendor-upstream/<ver短名>^{tree})
CHAIN=$(git commit-tree "$NEW_TREE" -p "$OLD" -m "baseline(vendor): deepseek-harness <ver> pristine tree")
git update-ref refs/heads/baseline/vendor "$CHAIN"
```

读官方 release notes + `git log vendor-upstream/<旧>..<新>`，先形成文字摘要。

**阶段二 · 影响矩阵（只读，产出本次升级的 breakdown 文档，落地后删除）**

```bash
PREV=$(git rev-parse baseline/vendor~1)
git diff --name-only "$PREV" baseline/vendor > /tmp/upstream-files.txt   # 上游全部变更文件
git log --oneline "$PREV"..baseline/vendor                                # 上游提交列表
```

将变更文件与 §2 清单的锚点逐一求交集，矩阵中每个 fork 标注三种处置之一：

| 处置 | 判据（§0 铁律） |
|---|---|
| **自动保留** | 上游未触及该 fork 文件/hunk |
| **手工合并** | 有交集：在冲突处把定制重放到新版源码上，补 `Local fork` 注释 |
| **弃用** | 官方已实现同功能 → 用官方，删我方 fork |

同一份矩阵同时列出：**增**（上游新增能力，评估是否吸纳）、**减**（上游删除/重构项，跟进调整；含官方化后可删的我方代码）。此矩阵即 AGENTS.md 大任务流程的第②步拆分文档。

**阶段三 · 三方合并（在集成分支上，main 全程不动）**

```bash
OLD_BASE=$(git rev-parse baseline/vendor~1)
OURS=$(git commit-tree "$(git rev-parse main^{tree})" -p "$OLD_BASE" -m "ours: <旧版本> 整合包全量状态")
git switch -c upgrade/<ver> "$OURS"
git merge baseline/vendor        # merge-base＝旧官方 pristine 树
```

> 前提：main 工作区干净（AGENTS.md「编写代码前先检查工作区」同理）。带未提交改动执行阶段四的 read-tree --reset 会将其抹掉——本次成文时已实际踩过一次。

冲突＝fork 与上游变更的精确交集，按影响矩阵逐个裁决；矩阵标「自动保留」的项若意外出现在冲突里，说明该 fork 的锚点记录过期，修 §2。解决完冲突照常提交。

**阶段四 · 自检与回填 main**

先跑 §2.0 master grep + 高危单项自检（缺锚点＝丢失，回阶段三补），确认 main 工作区干净后：

```bash
git switch main
git read-tree -u --reset upgrade/<ver>
git commit -m "chore(upgrade): 基线升级 <ver>——三方合并产出"
```

main 保持线性历史、vendor 对象不进入 main 可达图；升级内容为一个原子提交。

**阶段五 · 验证门（口径不变）**：构建全绿 → 受影响测试 → 打包 → 全局安装起实例逐项实测（**必须含非 loopback 远程浏览器场景**，见 §7 教训）→ 用户测试通过才 push。

**阶段六 · 收尾**：更新 §1 基线表、AGENTS.md「关键事实」、PLUGINS.md；删除 breakdown 文档；`upgrade/<ver>` 分支保留至用户验收通过后再删。

### 3.2 中止与回退补充

- 阶段一～四全程不触碰 main：任何一步做废＝`git switch main && git branch -D upgrade/<ver>`，基线链如需回收用 `git update-ref refs/heads/baseline/vendor <上一hash>` 回退一格。
- 已落 main 后的回退仍按 §5（revert + 重打包）。

## 4. 防静默过期

整合包自维护基线，官方出新 tag 后按 §3 三方合并流程升级，避免「官方已升级、整合包还是旧版源码」的静默问题。升级前先读 §0 铁律与 §2.0 自检。

## 5. 回退

- 弃用 fork 前先 git 提交当前状态（可 revert）。
- 升级过程的中途回退见 §3.2（集成分支随时可弃）。
- 已落 main 后的回退 = git revert + 重新 `pnpm run build` + 重新打包（用户执行）。

## 7. rc.2 重 base 定制丢失审计与恢复记录（2026-08-23）

rc.2 重 base（提交 `767711ad`，上游整文件覆盖）静默丢失了 **三处** 语义级定制，
全部于 2026-08-23 由 Linux 实机部署暴露并恢复。本节是 §2.0 标记自检约定的事实依据：

1. **`dsh-client-ui-settings` scope 恒 host**：`index.ts` 镜像构造与 `settings-scope.ts`
   bind 两处被还原成官方 `isLoopback ? 'host' : 'memory'` → 远程（非 loopback）浏览器
   settings 整体进入 memory 终态：提供方目录报「settings are unavailable in this
   browser」、插件配置页静默空白。原 fork 见 `c8c8d489`。
2. **`dsh-host-directory-picker-browse` 默认工作目录**：`configuredStartPath()` 方法、
   `@deepseek-ai/dsh-settings` import、package.json 依赖与 tsconfig reference 被整体删除。
3. **`apps/cli` profile-boot HMR 降级门控**：plain-node 生产安装跳过 watcher 的
   `loader.internal` 门控被删，watcher 变成无条件挂载。

**教训**：「构建全绿 + 单测全绿」证明不了定制还在——三处丢失时两者都是绿的；
实例冒烟当时只验了 loopback 场景，也发现不了第 1 处。重 base 后必须跑 §2.0
标记自检 + 远程浏览器场景实测。
