# 整合迁移路线图（大宝贝定制版）

> 目标：把 deepseek-harness `dsh-v0.1.0-rc.7` 平铺为仓库根基线，再把 5 个插件项目
> （含 8 个 `@deepseek-ai/*` 同名 fork）整合进 harness 源码，整体构建成「大宝贝定制版」。
> 本文件是逐项映射 + 迁移顺序 + 验证口径。迁移前先读 [升级适配指南.md](升级适配指南.md) §0 铁律：
> **官方新版已实现同功能 → 优先用官方，弃用对应 fork/适配层。**

> 故迁入 harness `packages/<group>/<pkg>/` 并按官方分组规范命名（`@deepseek-ai/dsh-*`）。

| 插件 | 类型 | 建议落点（组） |

## 3. 关键架构问题（迁移第一步先解决）

1. **bake-in 装配点（已定位）**：官方首方插件的装配是
   `packages/bundle/base/cordis.patch.yml`（dsh-base，每个 profile 先应用，451 行 `- insert:` 行）+
   `packages/bundle/web-app/cordis.patch.yml`（web 模式补丁：host 行 + 浏览器 roster 的
   `dsh.client` 行）+ 用户 profile 层。要让自研插件「一装全有」：
   - **host 端**插件（门闸 / defaults / describe-image 等）→ 在 base 或 web-app 的
     `- insert:` 列表加一行 `{id, name}`；
   - **client 端**插件（桌宠 / 手机端 / task-board 等）→ 在 web-app 的「browser plugin roster」
     （`dsh.client` 行）加行。
   - **8 个 fork 不加行**，直接改现有行对应包源码（§1 落点）。
2. **命名/ctx-key**：每个组 README 维护「package/ctx-key 映射」，迁入后需同步更新
   `packages/<group>/README.md` 与 `packages/README.md` 层级表。
3. **客户端 bundle 纯度门**：client 插件 bundle 只能 require 平台表 + INLINE_SAFE 白名单
   （参照 `packages/client` 现有 tsdown 预设），迁入后需过构建纯度门。

> 已核对：rc.7 把重试**执行**拆到官方 `@deepseek-ai/dsh-llm-retry`（base 装配 `llm-retry` 行，
> 监听 `agent/request-error` 执行退避），但**策略解析仍在各 adapter 内**：`resolveRetryPolicy(undefined)`
> 返回默认 maxRetries=2（非 undefined），所以 deepseek/pi-ai 各自在 `resolveAdapterOptions` 解析策略、
> 绕过 `dsh-llm` prepareRoutes 的通用兜底——重试兜底 fork 需在**三层**分别重 base
> （`dsh-llm` prepareRoutes + `dsh-llm-deepseek`/`dsh-llm-pi-ai` 各自的 resolveAdapterOptions）。

## 4. 迁移顺序

1. 纯插件（自包含、不碰官方包）：先 `dsh-mobile-adapt` / `deepseek-pet`（前端，改完刷新即生效）→
   `dsh-defaults` + `dsh-client-ui-defaults` → 门闸（host + client）→ task-suite 拆分。
2. 8 个同名 fork（重 base rc.7 源码）：先核对官方化，逐个改 `packages/<group>/<pkg>/src`，
   每个 fork 迁移后 `pnpm run build` + test-env 验证。
3. 装配：把迁入的插件注册进产品装配（preset / composition），确保 `pnpm dsh web` 默认带齐。
