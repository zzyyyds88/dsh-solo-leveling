# 开发规范（Development Standards）—— 开发时强制遵从

> 本文件是**本工作区开发时强制遵从的规范**，人类与 AI 代理一视同仁。依据：DeepSeek Harness 官方开发文档（<https://deepseek-harness.github.io/deepseek-harness/develop/basic/>）＋本工作区沉淀的项目经验。冲突裁决：铁律（AGENTS.md）> 本文件 > CONTRIBUTING.md 其余章节。

## 1. 上游规范摘要（官方文档原文要点）

### 1.1 插件基本形态（develop/basic）

- 插件是导出 `name` 与 `apply(ctx)` 的 TypeScript 模块；`apply` 里通过 `ctx` 注册能力。三种形态：函数 / 对象 / 类（需对外提供服务时用类， `extends Service` + `static inject`）。
- 依赖服务用 `inject: ['tools', ...]` 声明——框架保证依赖就绪后才调用 `apply`。
- 通过 `ctx` 注册的一切（事件监听、工具、定时器）在插件卸载时**自动清理**；手工资源用 `ctx.effect(() => () => cleanup())` 声明清理。

### 1.2 插件配置（develop/basic/config）

- 可调参数**一律做成配置字段**，禁止硬编码（检验标准：能否在 cordis.yml 中改这个值而不改代码？）。
- 导出 `Config` 类型 + 同名 Schemastery schema（`Schema.object(...)`），默认值直接写在 schema 里；不要导出普通对象当 Config。
- **配置错误要响亮**：schema 表达完备约束，非法配置在插件加载时失败报错。
- 配置变更触发 HMR：框架卸载旧实例、加载新实例；注册都在 effect 里，自动清理，不留旧实例残留。

### 1.3 打包与安装插件（develop/basic/publish）

- **分发必须带构建产物**：git 安装拉的是源码、不跑 build，没有 `lib/` 就加载失败。三种可行分发方式：
  1. 发布 npm（`pnpm publish` 时构建好 `lib/`）；
  2. 交付 tarball（`pnpm pack`，用户 `dsh plugin add ./xxx.tgz`）；
  3. git 安装（`dsh plugin add github:you/hello-plugin`）→ 作者必须提供 **自包含的 prepare 脚本**（不能依赖仅开发环境才有的 monorepo checkout），且用户需显式授权 `allowBuilds`。
- git 安装务必**锁定 commit**（`github:you/hello-plugin#<sha>`），只对源码可信的包授权（prepare 脚本会在安装时执行代码）。

### 1.4 使用 Web UI（guide/quickstart）

- `dsh` 进程把调用目录作为默认文件系统位置；Web UI 需先「选择工作区」选中项目目录后会话输入框才可用。模型密钥在设置 → 模型配置，立即可用无需重启。

## 2. 本工作区强制规范

### 2.1 版本控制（Git）

- 工作区根目录是单一 git 仓库，默认分支 `main`；**每次有意义的改动即提交**，提交信息用 Conventional Commits：`type(scope): subject`，type ∈ `feat|fix|chore|docs|test|refactor|perf`；提交信息避免 emoji。
- **禁止提交**：`node_modules/`、构建产物（`lib/`、`dist/`、src 下的编译输出）、第三方参考快照（`dsh-web-ui-main/` 已删除，按 `开发备忘.md` 加速命令可重新下载）、日志、密钥/口令（正式环境的 credentials/settings 不得入库）。
- **历史重写前必须备份**：任何 `git filter-branch` / `filter-repo` / `rebase` 等改写历史或强制推送的操作，**先 `git bundle create <备份>.bundle <ref>` 备份全部分支**；注意 filter-branch 会把不再出现在新历史中的已跟踪文件从工作区删除——重写后如发现工作区文件消失，立即从备份恢复（勿先跑 `git gc` 清对象）。
- 上传 GitHub 开源前：确认无敏感信息、补 LICENSE、打仓库 topic 标签（`dsh`、`dsh-plugin`、`deepseek-harness`、`plugin`），详见 CONTRIBUTING.md「发布到 GitHub 开源」。

### 2.2 代码与构建

- 本仓库 = harness fork 整合包：改插件 / 改官方包 = 改 `packages/<group>/<pkg>/src` → `pnpm run build` → 本地打包验证。**禁止直接手改 node_modules / 产物（lib/*.js）。**
- 新插件包命名：`dsh-` 前缀；UI 类 `dsh-client-ui-*`、后端 `dsh-host-*`。
- 代码、注释、文档、提交信息避免 emoji（对标 dsh-web-ui 全仓规则）。
- 语法/格式校验：改动后 `node --check`（JS）或项目构建脚本把关。

### 2.3 测试纪律

- 所有打包测试只在独立实例（非 3080 端口）进行，**正式实例（3080）不做任何实验**；正式安装只能由用户手动执行。
- 验证结论逐条记录（做了什么、为什么、怎么验证、怎么回退），随 git 提交。

### 2.4 文档纪律

- 工作区文档：根 `README.md`、`PLUGINS.md`、`CONTRIBUTING.md`、`AGENTS.md` 与 `docs/`（`开发规范.md` + `升级适配指南.md`）；行为变更时文档同步更新，根 README 与 PLUGINS 保持同步（见 AGENTS.md 工作流速查）。

### 2.5 插件配置入口规范（GUI 设置页）

**所有插件的配置入口统一放在「设置 → 插件 → 插件配置」区，以独立卡片形式呈现（注册 `settings.plugin.item` 槽位），禁止使用独立标签页（`settings.plugins.tab`）。** 样式与交互对齐官方「网页搜索」卡片。

卡片必备要素：

- **可展开/收起**的头部：标题 + 一句话描述；有未保存改动时显示「未保存」标记。
- **字段区**：每个字段 = 标签 + 输入控件 + 说明（hint）；字段值显示当前生效值。
- **保存 / 放弃**按钮：保存才写命名空间（staging 语义），放弃还原未保存改动；不可写时显示只读提示并禁用输入。

实现骨架（参照 `dsh-defaults/packages/dsh-client-ui-defaults/lib/client.js` 的 `DefaultsCard`）：

```js
// 注册（bundle 的 apply 中）
ctx.slots.inject("settings.plugin.item", function* () {
  yield ctx.slots.register({
    name: "settings.plugin.item",
    id: "<插件 id>",          // 唯一，如 "dsh-defaults"
    order: 30,                // 30+ 排在官方卡片（bash/agent-loop/web-search）之后
    locale: NS,
    inject: () => controller.inject(),   // { hooks: { <名称>: store }, save }
  }, CardComponent);
});

// 数据流
const scope = ctx.settingsScope.bind({ namespace: "<命名空间>" });  // 命名空间由宿主插件注册
// 组件内：const state = props.use<名称>((s) => s);   // hooks.X → useX 自动注入
// 保存：scope.set("字段", 值)；放弃：本地状态还原为 store 值
```

配套要求：

- 命名空间由对应宿主插件注册（`installSettingsSection`），并必须在 `dsh-host-apiproxy` fork 的 `exposedNamespaces()` 中暴露，设置面板才能读写。
- 配置项语义与存储：配置持久化于 `$DSH_HOME/settings.yaml` 的命名空间段；行为侧在**运行时读命名空间**（改设置即生效），避免写死/构建期注入。
- 文案（zh/en）用插件自己的 locale 命名空间注册。

## 3. 完成定义（Definition of Done）

一个改动「做完」的判定标准：

1. 语法/类型/构建通过（`node --check` 或 build.sh 全绿）；
2. 本地打包后在独立实例实测通过；
3. 有回退路径（.bak / 幂等脚本 / unpatch 说明）；
4. 文档同步（根 README / PLUGINS / 开发规范 / 升级适配指南，见工作区文档纪律）；
5. git 已提交（Conventional Commits），无敏感信息入库；
6. 若需正式安装：脚本交用户，在 SSH 终端手动执行，并更新根 README 项目清单。
