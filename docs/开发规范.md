# 开发规范（Development Standards）—— 开发时强制遵从

> 本文件是**本工作区开发时强制遵从的规范**，人类与 AI 代理一视同仁。
> 依据：DeepSeek Harness 官方开发文档（原文存档见
> [docs/上游开发规范/](上游开发规范/)）＋ 本工作区沉淀的项目经验。
> 冲突裁决：铁律（AGENTS.md）> 本文件 > CONTRIBUTING.md 其余章节。

## 1. 上游规范摘要（官方文档原文要点）

### 1.1 插件基本形态（develop/basic）

- 插件是导出 `name` 与 `apply(ctx)` 的 TypeScript 模块；`apply` 里通过
  `ctx` 注册能力。三种形态：函数 / 对象 / 类（需对外提供服务时用类，
  `extends Service` + `static inject`）。
- 依赖服务用 `inject: ['tools', ...]` 声明——框架保证依赖就绪后才调用
  `apply`。
- 通过 `ctx` 注册的一切（事件监听、工具、定时器）在插件卸载时**自动清理**；
  手工资源用 `ctx.effect(() => () => cleanup())` 声明清理。

### 1.2 插件配置（develop/basic/config）

- 可调参数**一律做成配置字段**，禁止硬编码（检验标准：能否在 cordis.yml 中
  改这个值而不改代码？）。
- 导出 `Config` 类型 + 同名 Schemastery schema（`Schema.object(...)`），
  默认值直接写在 schema 里；不要导出普通对象当 Config。
- **配置错误要响亮**：schema 表达完备约束，非法配置在插件加载时失败报错。
- 配置变更触发 HMR：框架卸载旧实例、加载新实例；注册都在 effect 里，
  自动清理，不留旧实例残留。

### 1.3 打包与安装插件（develop/basic/publish）

- **分发必须带构建产物**：git 安装拉的是源码、不跑 build，没有 `lib/` 就加载
  失败。三种可行分发方式：
  1. 发布 npm（`pnpm publish` 时构建好 `lib/`）；
  2. 交付 tarball（`pnpm pack`，用户 `dsh plugin add ./xxx.tgz`）；
  3. git 安装（`dsh plugin add github:you/hello-plugin`）→ 作者必须提供
     **自包含的 prepare 脚本**（不能依赖仅开发环境才有的 monorepo checkout），
     且用户需显式授权 `allowBuilds`。
- git 安装务必**锁定 commit**（`github:you/hello-plugin#<sha>`），只对源码
  可信的包授权（prepare 脚本会在安装时执行代码）。

### 1.4 使用 Web UI（guide/quickstart）

- `dsh` 进程把调用目录作为默认文件系统位置；Web UI 需先「选择工作区」选中
  项目目录后会话输入框才可用。模型密钥在 设置 → 模型 配置，立即可用无需重启。

## 2. 本工作区强制规范

### 2.1 版本控制（Git）

- 工作区根目录是单一 git 仓库，默认分支 `main`；**每次有意义的改动即提交**，
  提交信息用 Conventional Commits：`type(scope): subject`，type ∈
  `feat|fix|chore|docs|test|refactor|perf`；提交信息避免 emoji。
- **禁止提交**：`node_modules/`、测试环境运行态（`test-env/` 除 README.md）、
  第三方参考快照（`dsh-web-ui-main/`，可随时按 `开发备忘.md` 重新下载）、
  日志、密钥/口令（正式环境的 credentials/settings 不得入库；测试口令属测试
  环境专用，仅存于 test-env/settings.yaml）。
- 上传 GitHub 开源前：确认无敏感信息、补 LICENSE、打仓库 topic 标签
  （`dsh`、`dsh-plugin`、`deepseek-harness`、`plugin`），详见
  CONTRIBUTING.md「发布到 GitHub 开源」。

### 2.2 代码与构建

- 插件只基于官方 NPM SDK（`@deepseek-ai/*`），**禁止修改 DSH 源码**、禁止
  tsconfig 指向任何 DSH 源码 checkout；类型只从 node_modules 解析。
- 改插件 = 改源码（src/）→ 构建（tsdown）→ `lib/` 产物入库（git 安装依赖
  预构建产物）→ 装进 `test-env` 验证。**禁止直接手改 node_modules / 产物。**
- 新插件包命名：`dsh-` 前缀；UI 类 `dsh-client-ui-*`、后端 `dsh-host-*`。
- 代码、注释、文档、提交信息避免 emoji（对标 dsh-web-ui 全仓规则）。
- 语法/格式校验：改动后 `node --check`（JS）或项目构建脚本把关。

### 2.3 测试纪律

- 每个项目自带 `verify.sh`；所有打包测试只允许在 `test-env/`（端口 3090）
  进行，**正式实例（3080）不做任何实验**；正式安装只能由用户手动执行。
- 验证结论逐条写入项目 `变更记录.md`（做了什么、为什么、怎么验证、怎么回退）。

### 2.4 文档纪律

- 每个项目必须维护：思路库 README、`升级后重打补丁指南.md`、`变更记录.md`、
  `本次diff.patch`；涉及行为变更时文档同步更新。
- 根目录文档：`README.md`（工作区 + 项目清单）、`CONTRIBUTING.md`、
  `AGENTS.md`、`docs/`（开发规范与上游存档）。

## 3. 完成定义（Definition of Done）

一个改动「做完」的判定标准：

1. 语法/类型/构建通过（`node --check` 或 build.sh 全绿）；
2. 在 `test-env`（3090）实测通过并记录到 `变更记录.md`；
3. 有回退路径（.bak / 幂等脚本 / unpatch 说明）；
4. 文档同步（README / 变更记录 / 升级后重打指南）；
5. git 已提交（Conventional Commits），无敏感信息入库；
6. 若需正式安装：脚本交用户，在 SSH 终端手动执行，并更新根 README 项目清单。
